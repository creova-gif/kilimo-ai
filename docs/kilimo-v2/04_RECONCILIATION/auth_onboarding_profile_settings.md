## Summary

- Decision counts are in the table at the end of this section (computed from the Matrix below).
- Figma frames reviewed: 42 (7 Auth, 14 Onboarding incl. 2 superseded, 8 Profile, 10 Settings incl. 1 superseded, 3 Permission). Legacy routes/files covered: 27 rows + step-level rows for `onboarding.tsx`.
- **Biggest finding 1 — probable client/session split [code-read].** Five separate `createClient()` calls exist (`lib/supabase.ts:18`, `hooks/useAgroAuth.ts:75`, `hooks/useTasks.ts:109`, `hooks/useMarketIntelligence.ts:103`, `app/otp-auth.tsx:35`), none configured with an auth storage adapter. The OTP session is created inside `useAgroAuth`'s private client. `mintAgroId()` (`lib/agro/mintId.ts`), the farmer-profile sync in `edit-profile.tsx:~226` (`getSession()` then early `return`), `verification/business.tsx` and the onboarding `submit-verification` call all use the `lib/supabase.ts` client, which probably has no JWT, so the edge functions would answer 401 and the code silently falls back (local Agro-ID, swallowed try/catch, no upsert). The backend is proven correct with a real JWT (116-check suite); what is unproven is that the *app* ever sends one. Cheapest confirmation: after a real onboarding on the simulator, `select count(*)` on `agro_profiles`, `farmer_profiles`, `verification_requests` in the local DB.
- **Finding 2 — "session" is a local flag.** `isAuthenticated` is a persisted Zustand boolean; `restoreSession` stores only the 1-hour access token (no refresh token) and calls `getUser(token)` without `setSession`. After an app restart or an hour, the UI still says signed in while server calls have no identity. `Profile → Ondoka` calls `resetOnboarding()` only (`(tabs)/profile.tsx:486`): it never calls `signOut`, never deletes the SecureStore token, and wipes the local farm profile.
- **Finding 3 — returning users are re-onboarded.** `OnboardingGate` (`_layout.tsx:231`) sends anyone with `!isAuthenticated` to `/onboarding`, and `useIdleTimeout` clears auth after 15 idle minutes, so an idle farmer is thrown back to phone + SMS OTP on a weak network. Figma has a Sign-In frame that legacy never built.
- **Finding 4 — mandatory NIDA gate with fake uniqueness.** Step 5 blocks registration on a valid 20-digit NIDA / 9-digit TIN / licence and "uniqueness" is checked against a client-side list seeded with two fake IDs (`useKilimoStore.ts:218`, `onboarding.tsx:383`). Not every smallholder has a NIDA; there is no automated verifier; the server never checks duplicates.
- **Finding 5 — Figma auth frames contradict the backend.** Sign-Up/Sign-In/Reset/New-Password frames assume passwords, Apple and Google sign-in; the backend is phone/email OTP only. 4 of 7 Auth frames are removed/duplicates. Also: Figma contains placeholder contacts (`+255 123 456 789`, `0800 123 456` vs `0800 110 120`), three different version strings (2.1.0, 2.4.0, 2.4.1) and template artefacts ("Label / Title / Search") inside 81:1940 and 81:2539.
- Known open UX defects confirmed in current source: CTA outside the `KeyboardAvoidingView` (`onboarding.tsx:555-639` vs footer at `:642`, G-018); raw English provider errors and hard-coded English `Alert` titles (`onboarding.tsx:375` `'Error'`, `err.message` at `:333-357`, G-019); English a11y labels on Swahili screens (`accessibilityLabel="Go back"`, `"Phone Number Input"`, `"Select region"` etc., G-017).

## Role & authorization notes

- Roles are client-selected labels. `farmer_profiles.role` has no `check` constraint and the owner-update RLS policy allows any value; `edit-profile.tsx` lets a user change role at any time. Nothing in `lib/access.tsx` (`MATRIX` per role) is enforced server-side.
- Legacy has 8 canonical roles, Figma 6, and the superseded Figma frame the legacy 8: reconcile (Open question 1). Whatever set is chosen, privileged or organisational roles (Coop Leader, Extension Officer, Finance) must be treated as *requests* pending verification, consistent with `verification_requests` being reviewer-only writable.
- `ai-admin.tsx` has no role gate at all and is reachable by URL; it should be removed from the farmer app rather than gated on a client-side role.
- `verification_status` can be changed only by the service role (RLS select-only for owners; tested "user cannot self-approve"). The client `updateAgroId({verificationStatus:'pending'})` calls in `verification/business.tsx` are UI-only and must not be treated as truth.
- Public `verify-agro-id` is intentionally unauthenticated and PII-free (asserted in the smoke suite), so the share sheet is safe to offer.
- Session authenticity depends on Finding 1; until one persisted client is used, "authenticated" in the UI does not imply a JWT on requests.
